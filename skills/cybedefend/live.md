# Live: the proven flaws, replayed on the application running here

A proof test shows a flaw in the code. A live replay shows it on the application as it runs: the real router, the real middleware, the real database driver. It also settles what a test could not: a guard forgotten on the line that mounts a route, a second request that arrives before the first one has finished.

Run it only when the user asks (`/cybedefend live`), after an audit. It starts the user's application on their machine: that is theirs to decide.

## What it never does

`<skill>/scripts/live.mjs` holds to these in code, and so do you:

- **Only the application this step started, on this machine.** `start` refuses a port that already answers: an application that is already running could be the user's own, with real data. `probe` refuses any address that is not `localhost` and any port but the one `start` opened, and follows no redirect.
- **Throwaway data only.** Start the application the way the repository documents for development, with a database of its own: the database of its compose file, a SQLite file in a temporary folder. Before you start it, read its configuration with `node <skill>/scripts/cybedefend.mjs show <file>`. If it names a host that is not this machine or a service of its own compose file (a managed database, a production URL), or a live key of a payment or e-mail provider, do not start it: say why in the report.
- **Nothing that reaches a third party.** No route that sends an e-mail or a text message, charges a card or calls a webhook, unless the development configuration replaces that provider with a stand-in. The usage statistics of the application's framework count too: `start` switches them off for the application it starts (`DO_NOT_TRACK=1` and the frameworks' own switches), and a command of the framework you run yourself before it (a database, a migration) takes the same in front: `DO_NOT_TRACK=1 WASP_TELEMETRY_DISABLE=1 wasp db migrate-dev --name init`.
- **A replay, never a scan.** A few requests for each finding you already hold, written by you. No fuzzing, no load, no tool pointed at the application unless the user asks for one by name.
- **It ends clean.** `begin` before anything is started, `stop` when you are done, whatever happened, then remove what `stop` lists (`docker compose -p <name> down -v`, the temporary folder) until `left` says nothing is left.
- **It installs nothing.** A tool the start needs and the machine lacks (a framework's command line, a runtime, a database server) is named to the user with the version the repository asks for, and the step stops there. Never install it, and never offer to: that is the user's machine.

## The steps

**Asked again, it is done again.** `/cybedefend live` typed a second time starts the application and replays the findings a second time: the user asked to see it run. A replay kept from an earlier run, even one `finish` still shows as current, is no reason to answer from the file. `begin` puts the earlier requests aside.

1. **Find how it starts**: the README, a compose file, a Makefile, the scripts of `package.json`. Take the lightest way that gives a working application (a development server before a full stack). If nothing says how, or it needs credentials you do not have, stop there and say so: the proof tests stand on their own.
   - Check first that what it needs is there: the command it runs (`command -v <tool>`, and its version when the repository pins one), then the files git does not hold. An environment file the README tells a developer to create from an example (`.env.example`, `.env.server.example`) is created from that example with made-up values, where the README says, and removed in step 6. Say both in one line before you start.
   - Then, before you start anything: `node <skill>/scripts/live.mjs begin`. It notes what git sees as changed and what Docker holds (containers, volumes, images), so that step 6 can say exactly what this step added.
2. **Start it**: `node <skill>/scripts/live.mjs start --port <port> -- <the command>`. The command runs in the folder you call it from (the application's own folder when its command line asks for it, or `--cwd <dir>`). It waits for the port to answer, and prints the application's last lines when it does not come up. A database the application needs is started first, the way the repository says (`docker compose -p cybedefend-live up -d db`). When that command fails, or the repository has none, do not try it twice: start one yourself, a pinned version, reachable from this machine only, under this step's name (`docker run -d --rm --name cybedefend-live-db -e POSTGRES_PASSWORD=<made up> -p 127.0.0.1:<a free port>:5432 postgres:16`), and give its address to the application in the environment file this step created. Give each command the answer it would wait for (a migration's name, a yes): nobody is there to type. When the documented command listens on another address than `localhost`, or would write its data next to the user's, start the application through its own options or a small launcher kept in a throwaway folder: never edit a file of the application to start it.
3. **Create the actors** with the application's own sign-up, through `probe`: a victim and an attacker, with made-up names and passwords. When the sign-up asks to confirm an e-mail address, the development setup says how: a switch of the framework that skips it in development, set in the environment file this step creates (Wasp: `SKIP_EMAIL_VERIFICATION_IN_DEV=true`), or the link the application prints in its own log (`.cybedefend/out/live-app.log`). The actors exist because the application created them: never write in its database by hand, even a throwaway one. When neither way is there, say so, and replay what needs no confirmed account. A request that went wrong by your own mistake (a wrong path, a link cut short) is dropped before you go on (`drop`, below): the evidence holds what the application answered, not your tries. `start` opens the run's live page in the browser again (not with `--no-open`, when nobody is at the screen): it shows the application as started, then each replay the moment its answer comes back. Tell the user in one line that it is open.
4. **Replay each proven finding that blocks**, the most severe first, eight at most. The same steps as its proof test, as requests:

   ```bash
   node <skill>/scripts/live.mjs probe --finding api/controllers/account_controller.go:171 \
     --note "the attacker's token deletes the victim's account: 200, and the account is gone" \
     -X DELETE -H "Authorization: Bearer <the attacker's token>" http://localhost:8080/accounts/1
   ```

   `probe` prints the answer for you to go on with, and keeps the request and the answer in `.cybedefend/out/live.json` with tokens, cookies and passwords masked. `--finding` is the finding's `file:line` and nothing else (a sign-up, a sign-in or a check around the replay takes no `--finding`); `--note` says what the answer shows, in a few words: it is the line the report prints, so write it after you have read the answer. A probe sent by mistake leaves the evidence with `node <skill>/scripts/live.mjs drop <its number>`; its number is not given again.
5. **Then the leads a test could not settle**, three at most.
6. **Stop**: `node <skill>/scripts/live.mjs stop`. It ends the application and what it started, then lists what appeared since `begin` and is still there, each with the command that removes it: the database with its volume (`docker rm -f -v cybedefend-live-db`), a volume a failed command left behind, what the start wrote in the repository (a migration created for this run), a tracked file its tooling rewrote (`git checkout -- <file>`: a lock file). Everything on that list is this step's, however old it looks: remove it, remove the environment files this step created, then run `node <skill>/scripts/live.mjs left` until it says nothing is left. What it names as built by this step and ignored by git (the installed dependencies, a build folder) stays: the next start is faster. An image it names stays on the machine: say it in the report, and say an image was pulled only when `left` names one. Never stop a process by its name (`pkill`, `killall`): it would take the user's own with it. A process that still holds the port after `stop` is named to the user. `stop` signals only the process `start` launched on this machine: `start` notes it outside the repository with a random token, its port and the start time the system gives it, and `stop` refuses a process id that is not a whole number above 1, one this machine has no note of, one noted on another port, and one whose start time changed since. When the first process has exited and left others in its group (a start script that launches the server and ends), `stop` ends that group. `begin` notes what was there outside the repository too, and `left` and `stop` count only from that note, never from the list `live.json` holds: `left` refuses to run without it. When a command refuses, it signals and lists nothing: say so to the user, and never stop a process or remove a container yourself by another way.
7. **Say what the replay showed**, finding by finding: seen live, or not reproduced live and why. Two numbers, never one for the other: how many findings block is the verdict's, as `finish` printed it (`VERDICT: NOT YET, 42 finding(s) block`); how many you replayed and saw live is yours. A replay that does not show the flaw is worth as much as one that does: the test may reach a path the running application guards elsewhere, and the user must know which. A lead the replay confirmed can be sent to the dashboard as proven, in `.cybedefend/out/assessments.json` ([assess.md](assess.md)): `"verdict": "proven"` with `"live": <the probe's number>`.
8. `node <skill>/scripts/cybedefend.mjs finish` again: the audit page gains what was seen live, request and answer, next to each finding. Just before its verdict it prints a block `THE LIVE REPLAY`: the line `LIVE: ...` (what the page holds), the application that ran, and what this step left on the machine. **Your answer to the user starts with that block, copied line for line in a code block**, never summed up or reworded, then the line `VERDICT: ...` as it is. A line of the block that asks for something (`stop`, `left`) is done first, and `finish` run once more. Under the block, your own words: step 7, finding by finding. Say nothing about the machine that the block does not say: what it lists as built by this step was built by this step, and nothing "was already there" unless you saw it there before `begin`.

A replay holds for the code it ran on. Once the application's code changes (a file edited after the replay, or a commit that touches the code), `finish` stops showing it as current and says how many requests it left out. A file put back as it was is no change. After `/cybedefend fix`, a new replay shows the same requests refused.

## When it cannot be done

Say it in one line and stop: no documented way to start it; a tool the start needs that this machine lacks (name it and its version); a start that needs a secret you do not have; a configuration that points outside this machine; a port that is already in use; an application that does not come up after two tries. The audit is complete without this step.
